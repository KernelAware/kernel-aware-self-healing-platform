## 5. Disk Detection Flow You Should Implement

Your disk detector should follow the same general process flow:

```text
1. Receive normalized rule object.
2. Read disk target.
3. Read disk metric and condition.
4. Convert user metric name to Prometheus metric name.
5. Build a Prometheus query using disk labels.
6. Read current disk value.
7. Compare value against threshold.
8. Track violation duration in Redis.
9. Create disk incident.
10. Send incident to decision engine.
```

Recommended metric mapping:

```python
DISK_METRIC_MAP = {
    "Disk Usage (%)": "disk_usage_percent",
    "Disk Read": "disk_read_speed_mb",
    "Disk Write": "disk_write_speed_mb",
    "Read IOPS": "disk_read_iops",
    "Write IOPS": "disk_write_iops",
    "Busy Percentage": "disk_busy_percentage",
}
```

For a mount-point target, the Prometheus query should be similar to:

```promql
disk_usage_percent{mountpoint="/data"}
```

For a device target:

```promql
disk_usage_percent{device="/dev/sda1"}
```

The disk incident should look like:

```json
{
  "rule_id": 12,
  "system_id": 1,
  "incident_type": "disk",
  "incident_severity": "Critical",
  "incident_priority": "High",
  "target": "/data",
  "target_type": "mountpoint",
  "violated_metric": {
    "id": 5,
    "metric": "Disk Usage (%)",
    "operator": "Greater Than (>)",
    "threshold": 90,
    "duration_seconds": 300
  },
  "value": 94.2
}
```

For disk duration tracking, do not use `pid`. The current duration function is process-specific:

```python
check_duration(system_id, pid, metric_name, duration_seconds)
```

You should either generalize it to:

```python
check_duration(system_id, target, metric_name, duration_seconds)
```

or create a disk-specific version using a Redis key such as:

```text
violation:disk:{system_id}:{target}:{metric}
```

## 6. Important Existing Problems

The following issues will affect your implementation:

1. `DiskDetector.detect()` currently only prints a message and returns an empty list in `disk_detector.py`.

2. `metrics_loader.py` only has process-oriented querying logic. Disk queries need `mountpoint`, `device`, or `filesystem` labels.

3. `check_duration()` requires a PID, which disks do not have.

4. The decision engine has no `"disk"` strategy in `decision.py`.

5. The healing sender is unfinished:
   - `healing_engine.py` contains `pass`.
   - `backend.py` contains unfinished incident storage.

6. `create_action_plan()` reads `decision["actions"]`, but the process decision returns `all_actions`.

7. Disk actions need to be clearly defined. Possible actions are:

```text
send-notification
run-command
run-automation
```

The healing engine currently supports `run-command`, but its command allow-list only contains:

```text
disk-usage
memory-usage
```

8. The backend currently forces every rule to:

```python
system_id = 1
```

9. The frontend uses disk labels such as `mountpoint`, but the exporter currently exposes disk metrics with `device`, `mountpoint`, and `filesystem`. The detector must use those exact labels.
